**Кейс по системной аналитике**

**Кейс 1. «Альфред, друг Бэтмена»**\
**TravelTech: сервис планирования путешествий. Описание сервиса:**

Сервис позволяет пользователю спланировать поездку: подобрать билеты,
отели, трансферы, активности. Все бронирования синхронизируются в едином
интерфейсе, система выдаёт рекомендации на основе интересов и истории.

**Типовые процессы:**

-   Поиск и бронирование билетов/отелей

-   Планирование маршрута путешествия

-   Синхронизация расписаний и уведомлений

-   Персонализированные рекомендации

-   Уведомления о задержках и изменениях

-   Обратная связь по поездке

**Особенности проектирования:**

-   Многопользовательский режим (семейные или групповые поездки)

-   Интеграции с внешними API (авиаперевозчики, букинги)

-   Обработка платежей, паспортных данных

-   Работа с тайм-зонами и международными форматами данных

**Вызовы**

-   Конфликты расписаний и пересадок

-   Персонализация без утечки данных

-   Надёжность при отказах внешних API\
    \
    **Задание. **Спроектируйте систему, которая:

-   Отслеживает статус рейсов пользователей (через внешние API или
    рассылки)

-   При обнаружении задержки/отмены --- уведомляет пользователя

-   Автоматически предлагает альтернативные рейсы или активности

-   Обновляет общий план путешествия

Учитывайте, что:

-   Данные о рейсах приходят с задержкой,

-   Пользователь может быть оффлайн,

-   Альтернативные варианты должны учитывать багаж, визы, таймзоны.

P. S. Нельзя хранить паспортные данные дольше, чем необходимо для
поездки.

Исходя из условия задачи, получается, что необходимо доработать текущий
сервис TravelTech. Для понимания доработки были взяты данные уже якобы
разработанного проекта [yn96k/traveltech-service: Кейс по системной
аналитике - сервис совместного планирования
путешествия](https://github.com/yn96k/traveltech-service/tree/main)

**Для начала выделим роли и права:**

Пользователь -- это обобщающая роль.

Участник группы -- это тот, кто предлагает варианты для бронирования.

Организатор поездки -- это тот, бронирует. Допустим, что может быть 2-3
организатора поездки.

**User Stories**

**US_1:** Как участник группы, я хочу видеть статус выбранного рейса с
отметкой времени последнего обновления, чтобы понимать, нужно ли
обсуждать новую корректировку плана.

**US_2:** Как организатор поездки, я хочу видеть статус выбранного рейса
с отметкой времени последнего обновления, чтобы принять решение об
утверждении последней версии плана.

**US_3:** Как пользователь, я хочу получать от системы альтернативные
варианты рейсов или активностей, учитывающие багаж, визы, таймзоны,
чтобы сэкономить время на корректировку плана.

**(**Отмечу, что в проекте было предусмотрено уведомление без уточнения
режима пользователя**) US_4:** Как участник группы, я хочу получать
уведомление о задержке/отмене рейса SMS, если у меня нет доступа к сети
Интернет, чтобы узнать об изменении и перейти к корректировке плана или
выбору альтернатив.

**US_5:** Как пользователь, я хочу, чтобы мои паспортные данные
автоматически удалялись из системы после завершения поездки, чтобы быть
уверенным, что моя конфиденциальная информация не будет храниться больше
продолжительности всей поездки и не будет украдена в случае утечки.

**US_6:** Как пользователь, я хочу указать данные о моих визах в своём
аккаунте (страна, срок действия, тип), чтобы система автоматически
предлагала мне подходящие альтернативные рейсы.
