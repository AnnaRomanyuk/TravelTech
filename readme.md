# Кейс по системной аналитике

## Кейс 1. «Альфред, друг Бэтмена»

**TravelTech: сервис планирования путешествий. Описание сервиса:**

Сервис позволяет пользователю спланировать поездку: подобрать билеты, отели, трансферы, активности. Все бронирования синхронизируются в едином интерфейсе, система выдаёт рекомендации на основе интересов и истории.

**Типовые процессы:**

- Поиск и бронирование билетов/отелей
- Планирование маршрута путешествия
- Синхронизация расписаний и уведомлений
- Персонализированные рекомендации
- Уведомления о задержках и изменениях
- Обратная связь по поездке

**Особенности проектирования:**

- Многопользовательский режим (семейные или групповые поездки)
- Интеграции с внешними API (авиаперевозчики, букинги)
- Обработка платежей, паспортных данных
- Работа с тайм-зонами и международными форматами данных

**Вызовы:**

- Конфликты расписаний и пересадок
- Персонализация без утечки данных
- Надёжность при отказах внешних API

---

## Задание

Спроектируйте систему, которая:

- Отслеживает статус рейсов пользователей (через внешние API или рассылки)
- При обнаружении задержки/отмены — уведомляет пользователя
- Автоматически предлагает альтернативные рейсы или активности
- Обновляет общий план путешествия

Учитывайте, что:

- Данные о рейсах приходят с задержкой
- Пользователь может быть оффлайн
- Альтернативные варианты должны учитывать багаж, визы, таймзоны

> **P. S.** Нельзя хранить паспортные данные дольше, чем необходимо для поездки.

Исходя из условия задачи, получается, что необходимо доработать текущий сервис TravelTech. Для понимания доработки были взяты данные уже якобы разработанного проекта [yn96k/traveltech-service: Кейс по системной аналитике — сервис совместного планирования путешествия](https://github.com/yn96k/traveltech-service/tree/main).

Для начала выделим роли и права:

- **Пользователь** — это обобщающая роль.
- **Участник группы** — это тот, кто предлагает варианты для бронирования.
- **Организатор поездки** — это тот, кто бронирует. Допустим, что может быть 2–3 организатора поездки.

## User Stories

**US_1:** Как участник группы, я хочу видеть статус выбранного рейса с отметкой времени последнего обновления, чтобы понимать, нужно ли обсуждать новую корректировку плана.

**US_2:** Как организатор поездки, я хочу видеть статус выбранного рейса с отметкой времени последнего обновления, чтобы принять решение об утверждении последней версии плана.

**US_3:** Как пользователь, я хочу получать от системы альтернативные варианты рейсов или активностей, учитывающие багаж, визы, таймзоны, чтобы сэкономить время на корректировку плана.

**US_4:** Как участник группы, я хочу получать уведомление о задержке/отмене рейса SMS, если у меня нет доступа к сети Интернет, чтобы узнать об изменении и перейти к корректировке плана или выбору альтернатив.

> (Отмечу, что в проекте было предусмотрено уведомление без уточнения режима пользователя.)

**US_5:** Как пользователь, я хочу, чтобы мои паспортные данные автоматически удалялись из системы после завершения поездки, чтобы быть уверенным, что моя конфиденциальная информация не будет храниться больше продолжительности всей поездки и не будет украдена в случае утечки.

**US_6:** Как пользователь, я хочу указать данные о моих визах в своём аккаунте (страна, срок действия, тип), чтобы система автоматически предлагала мне подходящие альтернативные рейсы.

## Use Cases

### UC-01 (интеграционный): Наличие статуса выбранного рейса с отметкой времени последнего обновления

| Поле | Значение |
|---|---|
| **Акторы** | Пользователь, Внешний сервис покупки билетов и т.д. |
| **Примечание** | Выделен новый внутренний микросервис «Сервис статус рейса», который направлен на синхронизацию статуса рейса из внешнего приложения с TravelTech. Выделен новый микросервис, а не добавлен функционал в Сервис синхронизации (функционал синхронизации оффлайн-правок), т. к. у функционалов совершенно разные источники данных, модели отказов и бизнес-цели, смешивание их в одном сервисе приведёт к высокому уровню связности и трудностям в поддержке. |
| **Предусловия** | 1. Пользователь авторизован в системе.<br>2. Система имеет активный план путешествия, содержащий хотя бы один рейс. |
| **Постусловия** | Пользователь видит статус рейса с отметкой времени последнего обновления. |
| **Основной поток** | 1. Пользователь открывает экран с деталями рейса.<br>2. Система отображает текущий статус рейса.<br>3. Система отображает время последнего обновления статуса. |
| **Альтернативный поток** | **A1_UC-01. Система получила данные от Внешнего сервиса покупки билетов и т.д., но время их обновления на стороне источника превышает допустимый порог свежести (например, больше 15 минут)**<br>1. Система отображает статус рейса и время его последнего обновления.<br>2. Система добавляет предупреждающий бейдж «Данные могут быть устаревшими». |
| **Исключения** | - **E1_UC-01. Внешний сервис покупки билетов и т.д. недоступен:** Система отображает последний сохраненный статус с пометкой «Данные могут быть устаревшими» и временем последнего успешного обновления.<br>- **E2_UC-01. Пользователь оффлайн:** Система отображает статус из локального кэша с пометкой «Нет соединения. Данные на [время]». |
| **Критерий приемки** | - Текущий статус рейса<br>- Наличие времени последнего обновления данных<br>- При недоступности внешнего сервиса отображается последний сохраненный статус с пометкой «Данные могут быть устаревшими» и временем последнего успешного обновления (для E1_UC-01)<br>- При недоступности сети отображается кэшированный статус с пометкой «Нет соединения. Данные на [время]» (для E2_UC-01)<br>- Предупреждающая подпись «Данные могут быть устаревшими» (для E3_UC-01). |

### UC-02: Получение от системы альтернативных вариантов рейсов или активностей

| Поле | Значение |
|---|---|
| **Акторы** | Пользователь, Сервис рекомендаций |
| **Триггер** | Система зафиксировала задержку/отмену рейса из активного плана путешествия и автоматически сформировала список альтернатив рейсов. |
| **Предусловия** | 1. Пользователь авторизован в системе.<br>2. Система имеет активный план путешествия, содержащий хотя бы один рейс. |
| **Постусловия** | Альтернативный вариант рейса добавлен в план путешествия. |
| **Основной поток** | 1. Пользователь открывает экран с информацией о сбое рейса.<br>2. Система предлагает открыть список альтернативных вариантов (рейсы или активности), ранжированных по релевантности.<br>3. Пользователь соглашается открыть список.<br>4. Система отображает список альтернативных вариантов.<br>5. Для каждого варианта система отображает ключевые параметры: совместимость с багажом, необходимость визы, корректный пересчет времени с учетом таймзон.<br>6. Пользователь выбирает понравившийся вариант.<br>7. Система добавляет выбранный пользователем вариант в план путешествия. |
| **Альтернативный поток** | **A1_UC-02. Нет подходящих альтернативных рейсов**<br>1. Система отображает ближайшие варианты с явной пометкой ограничений (например, «Требуется транзитная виза», «Багаж не включен»).<br>2. Решение о выборе принимает Организатор поездки.<br><br>**A2_UC-02. Нет рейсов вообще (полная отмена)**<br>1. Система предлагает альтернативные активности (например, сдвиг экскурсий, продление проживания в отеле).<br>2. Пользователь выбирает вариант. |
| **Исключения** | - **E1_UC-02. Внешний сервис поиска недоступен:** Система использует кэш последних успешных ответов. Если кэш пуст, Система отображает сообщение «Поиск альтернатив временно недоступен» и предлагает только альтернативные активности из БД рекомендаций.<br>- **E2_UC-02. У пользователя не указана виза:** Система предлагает варианты без учета визы, добавляя пометку «Визовый статус не проверен».<br>- **E3_UC-02. Пользователь оффлайн:** Система сохраняет запрос на подбор альтернатив и отправляет его через SMS (UC-03). |
| **Критерий приемки** | - Отображается список альтернатив, содержащий параметры совместимости (багаж, визы, таймзоны).<br>- Пользователь может выбрать альтернативный вариант.<br>- При отсутствии подходящих рейсов отображаются варианты с явными пометками ограничений (для A1_UC-02).<br>- При полной отмене предлагаются альтернативные активности (для A2_UC-02).<br>- При недоступности сервиса поиска отображается сообщение об ошибке «Поиск альтернатив временно недоступен» и предлагаются активности из кэша (для E1_UC-02).<br>- При отсутствии информации о визе варианты помечаются «Визовый статус не проверен» (для E2_UC-02).<br>- При оффлайне пользователя отображается кэшированный список с пометкой «Нет соединения» (для E3_UC-02). |
